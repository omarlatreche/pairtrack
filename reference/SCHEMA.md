Source analysed: the live job-pack workbook (58 KB). Its filename carries the exchange
code and a project number and is deliberately not recorded here.
**This document deliberately contains no real cell values.** Patterns use `#` for a
digit and `A` for a letter. It is safe to commit.

## Workbook

- One worksheet, named for the exchange and its code
- The data is a real **Excel Table** named **`Job_pack`**, range **`A1:I443`**,
  `tableType="queryTable"` — the pack is generated by a Power Query / data connection,
  so the shape should be stable week to week. **Read the table, not the used range.**
- **9 real columns (A–I), 442 job rows**, header on row 1.
- Columns **J–N are empty** but carry formatting, so a naive reader reports 14 columns.
  Ignore any column outside the `Job_pack` table range.
- No merged cells, no hidden rows or columns, no defined names, no formulas, no
  autofilter, no second sheet.

## What this pack actually is

Every row moves one circuit **off one of 5 old equipment shelves onto a single new
shelf**. It is an **exchange equipment migration / re-jumpering pack**, not a fault-repair
pack. That is why the workflow gates are *Ready to activate → Test → Completed*.

## Three job types, and they are not the same work

Derived from whether `ESIDE TIES` / `DSIDE TIES` are populated:

| Type | Count | Meaning |
|---|---|---|
| **No ties** | **217** | Direct MDF jumper — bar pair straight to new equipment. |
| **E/D-side ties** | **222** | Tie-cable route via E-side and D-side references. More work per job. |
| **LLU ties** | **3** | LLU tie format (`…X…  I` in / `…Y…  O` out). Rare, likely handled differently. |

The job type is **not a column** — it must be derived on import. Badge it on the card.
The mix is roughly 50/50, so an engineer planning a day needs to see it at a glance.

Job type does **not** correlate with `Job Number` prefix or old shelf — all three types
appear across all prefixes and shelves. It has to be derived per row.

## `MDF BAR PAIR` — the key to work order

Format: `<frame>/<block><number>`, e.g. `##/A###`.

- **Frame `01`: 415 jobs**, across **17 blocks** — `A B D E F G H J K L N P R S T U W`
  (block letters skip `C I M O Q V`).
- **Frame `09`: 26 jobs**, single block `INTL` — physically a different part of the site.
- Block sizes are very uneven: largest ×58, smallest ×5.

**Parse this into `{ frame, block, number }` on import.** Sorting by frame → block →
*numeric* number is the order the engineer physically walks the frame. Sorting the raw
string alphabetically is wrong (`A10` would sort before `A9`).

## Known defects in the source data — handle, don't crash

Two rows in 442 are malformed. The importer must accept them, flag them, and let the
engineer fix them in-app:

1. **`Old_Equipment` malformed on 1 row** — pattern `########.` with an empty port
   segment, i.e. the shelf and port ran together and the port was lost.
2. **`MDF BAR PAIR` invalid on 1 row** (the last row of the pack) — the value is a bare
   `0` instead of a frame/block reference. This row cannot be placed in frame-walk order;
   sort it into an "Unplaced" group at the end rather than dropping it or crashing.

Add both as importer unit-test cases.

## Import gotchas

- **`New_Equipment` and `Old_Equipment` values contain a literal leading apostrophe**
  (`'###.####`) in the cell value itself — not merely an Excel quote-prefix flag.
  **Strip a leading `'` from every string cell on import**, then keep the rest verbatim.
- `Circuit` is text, not a number — never let a parser coerce it and lose the leading `0`.
- `JOB` is the only genuine integer column.
- `ESIDE TIES` / `DSIDE TIES` contain **internal spaces** in the LLU format — do not trim
  interior whitespace, only the ends.

## Constant columns

`DB` has exactly one value across all 442 rows. A column with cardinality 1 is worth zero
screen space on a phone. **Detect constant columns generically on import**, show them
once in the pack header, and keep them out of the card and out of the sort list. Do not
hard-code `DB` — next week's pack may have a different constant column.

## The progress columns are the app's, not the sheet's

The source file has **no** `Ready to Activate`, `Activation Timestamp`, `Test Status`,
`Notes`, `Completed By` or `Timestamp` column — those exist only in the tool from the
reference screenshots, appended after column I. Likewise `VERT` and `UP` are
engineer-entered in that tool, not present in the sheet.

So: columns A–I are **read-only imported truth**; everything else is app-owned progress.
Export writes A–I back verbatim and appends the progress columns after them.
